# 小可 Wiki 文风卡

来源：`模块开发指南`、`适配器开发指南`、`自搭建指南`、`wiki` 模块页、`可调用对象列表` 五篇。

## 一句话

教程式技术说明：直接称“你”，用短句把操作、结果和边界按顺序讲清。不设问，不煽情，不写空泛的过渡。

## 语气与人称

- 读者称“你”，机器人称“机器人”，不使用“我们”。
- 开篇直接说明本页讲什么，一句话交代范围。不写“本文将会教你……”“本文将会介绍……”。
- 需要读者操作时用“请……”，条件用“若……”“如果……”，判断用“可以”“需要”“支持”“不支持”。
- 陈述功能用“此模块可以……”“此命令用于……”“此方法用于……”，不写口号式的功能说明。
- 语气平实，不热情推销，不用感叹号。

## 句子

- 平均 35–50 字；一句话只承载一个动作、条件或结果。
- 不用分号。并列内容拆成两句，或改成列表。
- 少用连续定语。把一串“的”拆成两句，先说对象，再说条件或动作。
- 指代明确。重复写“此命令”“此模块”比堆“它”“其”更好读。
- 读起来卡住时，先找主语和动作，按“谁做什么、结果是什么”重写，再拆句。不要只换同义词。
- 同一段里并列三个以上事实时，改成列表；不要用逗号或“与”把事实串成一句。

## 防御性句子

- 只写实际存在的行为和约束。不要写“适配器不直接调用 Server 内部函数，也不自己写配置文件”“CLI 不依赖 core”“不会创建文件”这类解释“不做什么”的句子；读者用不到这些否定说明。
- 确实需要限制时，写成可执行的条件和结果。例如“命令级权限只能追加更严格的要求，不能降低模块门槛”。
- 不写“不是……而是……”的对照句，也不替读者预设疑问。
- 前因后果按“默认行为 → 失败结果 → 何时例外”排列。例如敏感信息检查：默认执行扫描；不通过时整条消息链被替换；确认内容安全时才跳过。

示例：

> 若页面中存在 Infobox，则会渲染并展示页面中的 Infobox 图片。

> 如果不打算支持此方法，直接在方法定义下设为 pass 即可。

## 段落

- 一段 1–3 句，先给结论，再补原因或边界。
- 长段落指连续正文超过 80 个汉字，且没有分段、列表、小标题或引用块分隔。超过就按语义拆成 2–3 段，不要按句号机械切。
- 代码块前用“示例：”“以下为……”“例如：”引出，说明这段代码做什么。
- 代码块后用“说明：”接列表，逐条解释参数、行为或限制。
- 段落之间靠“若”“当”“因此”承接，不用空泛的过渡语。

## 标题

- 用名词或动宾短语：`介绍`、`包结构`、`最小实例`、`创建实例`、`注册命令`、`命令语法模板`、`正则与定时任务`、`权限`。
- H2 放主题，H3 放子主题，H4 放同一功能的变体或模式。
- 模块页直接用命令名作 H2；教程页用步骤或主题作 H2。
- 不用问句标题，不用空泛的标题。

## 模块使用页

- 开头一句“此模块可以……”，说明用途和适用场景。
- 使用页只写命令行为与结果。配置字段、权重、数据表等技术细节放“安装与开发”页。
- 命令前先列权限（`公开`、`仅管理员`、`仅超级用户`），再写“用法：”和命令。
- 有选项时写“选项：”，每个选项一条。
- 正文按“这条命令做什么 → 参数怎么传 → 结果是什么 → 什么情况下失败”展开。
- 多命令模块按命令拆 H2，不为凑结构强行分组。
- 保留 `CommandUsage`、`ChatExample` 的原有属性和示例内容。

## 教程与开发页

- 先讲目标、前置知识和目录结构，再给最小可运行示例。
- 每节开头用一句话说明“这节讲什么”，然后给代码，再用“说明：”解释。
- 参数、字段、模式用列表逐条写，不塞进长段落。
- 安装、配置、调试按实际执行顺序排列。
- 结尾停在最后一个技术点，不写空泛的收尾。

## 参考页

- 开头用“本文整理了……”，说明覆盖范围。
- 每个对象一个 H2，每个方法一个 H3。
- 方法先给签名代码块，再列参数、返回值、异常；不写教程步骤。
- 目录只列对象名，不重复正文说明。

## 用词

- 解释性正文用日常技术中文。能用具体动作说清，就不用抽象名词。
- 英文缩写、字段名、命令名只在需要精确指代时保留。第一次出现时，用一句中文说明它指什么。
- 同一概念全页用同一个词，不为了显得专业换同义词。
- 不把英文句子逐词翻成中文。先想清楚这句话在说谁做什么，再用中文重新说一遍。
- 句子里的动作要有明确的主语。需要读者操作时，直接写“你”要做什么。
- 不用生硬的名词化动词。写“监控”“交给……处理”“升级操作”“最多等待 10 秒”，不写“监督”“转交”“升级请求”“等 10 秒”。
- 不用缩略名词代替具体对象。写“这个包”“明确授权”“迁移编号”“新增的 key”，不写“同一分发”“显式授权”“号段”“新键”。
- 不写“决定”。按语境写“确定”“取决于”“控制”“从……读取”或“取”。“装载”按安装语境写“加载”。
- 不把“消息链”缩成“链”。写“整条消息链”“新的消息链”。
- 说口令确认时写“原样回复这个口令”，不写“完整回复该口令”；说等待方法取走消息时写“取走”，不写“消费”。

示例：

- 安装前先检查依赖是否齐全。
- 新配置只写进这个实例自己的表。
- 命令执行完后，把结果返回给用户。

## 版本与数量

- 不把版本号、包数、页面数、模块数写死在正文。它们的值来自包清单、`pyproject.toml`、主题清单或当前仓库，写死后很快会过期。
- 说明前置条件时，写“版本要求见 `docs-theme.json`”或“由主题清单声明”，不要复述具体版本号。
- 描述范围时用“当前仓库中的模块”“每个内置模块”“相关页面”，不要写“有多少个模块”“有多少个页面”这类汇总数字。
- 行为限制是另一回事。例如“最多处理 5 个页面”是代码里的上限，可以保留，但要写清它是行为限制，不是仓库统计。
- 示例输出里的版本号和数量只是示例值，不要当成规格。能改用占位符的就用占位符。
- 依赖约束不要手写版本范围。正文用 `PackageDependencies` 组件，数据由构建时读取包元数据生成。
- 配置模板、接口文档里无法组件化的契约值，按源码原样保留，不要为了去掉数字改动语义。

## 路径与配置

- 包文档目录统一写 `docs/`，不要写旧路径 `doc/`。旧路径只在兼容说明里出现。
- 包文档元数据的默认层是 `docs/config/global/docs.global.toml`，用户覆盖层是 `docs/config/docs.toml`。JSON 版本使用同名 `.json`。
- 实例配置的默认层是 `config/global/<表名>.global.toml` 或 `.json`，用户覆盖层是 `config/<表名>.toml` 或 `.json`。
- `global` 是只读默认层，保存配置只写用户层。用户层没有的键回退到默认层，删除用户键后也回到默认值。
- 写配置说明时先交代默认值来自哪个文件，再写用户层如何覆盖。不要把手写的默认值写成唯一来源。
- 路径、文件名、表名以当前代码和配置为准；不要把旧目录、旧文件名写进操作步骤。

## API 链接

- 核心文档正文里的 API 名称不要手写链接。生成器在构建时按导出清单自动加链接。
- 只链接导出清单里有独立条目的名字。方法名按当前类上下文匹配；跨类时写完整名，例如 `Bot.post_message`。
- 代码块、已有链接不处理。别名、属性或没有独立条目的名字保持纯文本。

## 依赖

- 正文的依赖段用 `<PackageDependencies package="<包 key 或分发名>" />`，不写 `>=`、`<=` 这类范围。
- 组件读取已装包的 `Requires-Dist`，跳过 `extra` 可选依赖。生成器同时按包 key 和分发名建立索引。
- `pyproject.toml` 示例只写包名，并说明实际版本范围从包根的 `dependencies` 读取。
- 组件只在 VitePress 构建产物中渲染。包内 Markdown 仍应能直接读懂。
- 代码块里的依赖示例、`manifest.toml` 的接口字段属于契约，不强行改成组件语法。

### 抽象名词与口号

遇到这些词，先问它指哪个具体动作、对象或结果，再用一句话写出来。不要换成另一个抽象词：

收口、对齐、拉齐、闭环、复盘、赋能、抓手、颗粒度、心智、认知、范式、协同、联动、打通、收敛、沉淀、落地、串联、全链路、顶层设计、组合拳。

### 检查方法

- 改写后逐个搜索上表里的词，命中就按上下文重写整句。
- 不要用批量替换脚本处理这些词。同一个词在不同句子里可能需要不同的说法。
- 替换后复读前后句。句子要能独立读懂，不能只把词换掉。
- 搜索正文里的 `doc/`，确认没有把 `docs/` 写成旧路径；兼容说明例外。
- 搜索正文里的 `>=`、`<=`、`==`，确认依赖段使用组件，代码块和接口字段例外。
- 搜索 `config/global` 与 `docs/config/global`，核对默认层、用户层和回退关系的描述。

## 格式

- 命令统一用 `~` 前缀；标识符、路径、字段、配置键用行内代码。
- 代码块标语言；命令块保留可直接复制的形式。
- 表格用于参数、字段、权限和平台对照；步骤和注意事项用列表。
- 中文正文用中文引号；代码、命令、URL 原样保留。
- 数字、单位、默认值、版本号照原文，不改写。
- 源码里的用户可见文案与文档同口径。用词调整涉及用户可见文案时，locale、界面文案、示例输出一起改；`mute`、`muted` 这类代码标识符保持原样。

## 逐句复读

改写完成后逐句检查，不能只替换词：

- 主语是否明确，动作与对象是否齐全。
- 前后句是否承接，代词指代是否清楚。
- 能否换成更常见的动词或更短的说法。
- 是否还有连续三层以上从句，或一句话里塞了多个条件。
- 读起来不顺就重写整句，不要只改标点。

## 禁止

- 问句标题，或介绍“本文按什么顺序展开”的句子。
- 口号式、推销式、空洞总结式的表达。
- 长分号链、连续三层以上从句、没有具体内容的背景铺垫。
- 连续正文超过 80 个汉字仍不分段。
- 用旧称代替“禁止发言”，或让文档与源码文案不一致。
- 手写依赖版本范围，或把配置默认值只写在正文里而不指向 `global` 文件。
- 把 `docs/` 写成旧路径 `doc/`，除非在说明兼容读取。
- 比喻、拟人、感叹号、表情符号。
- 为了“更完整”而新增未核实的行为、参数或默认值。
- 改写组件属性、表格数据、代码块、图注和示例对话。
