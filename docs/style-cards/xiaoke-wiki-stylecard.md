# 小可 Wiki 文风卡

来源：`模块开发指南`、`适配器开发指南`、`自搭建指南`、`wiki` 模块页、`可调用对象列表` 五篇。

## 一句话

教程式技术说明：直接称“你”，用短句把操作、结果和边界按顺序讲清。不设问，不煽情，不写空泛的过渡。

## 语气与人称

- 读者称“你”，机器人称“机器人”，不使用“我们”。
- 开篇直接说明本页讲什么，一句话交代范围。不写“本文将会教你……”“本文将会介绍……”。
- 需要读者操作时用“请……”，条件用“若……”“如果……”，判断用“可以”“需要”“支持”“不支持”。
- 陈述功能用“此模块可以……”“此命令用于……”“此方法用于……”，不写口号式的功能说明。
- 语气平实，不热情推销，不用感叹号。

## 句子

- 平均 35–50 字；一句话只承载一个动作、条件或结果。
- 不用分号。并列内容拆成两句，或改成列表。
- 少用连续定语。把一串“的”拆成两句，先说对象，再说条件或动作。
- 指代明确。重复写“此命令”“此模块”比堆“它”“其”更好读。
- 读起来卡住时，先找主语和动作，按“谁做什么、结果是什么”重写，再拆句。不要只换同义词。
- 同一段里并列三个以上事实时，改成列表，不要用逗号或“与”把事实串成一句。
- 叙述句、代码注释和 docstring 不使用“xxxx：yyyy”说明式冒号句，不把冒号当万能连接词。按语境改写为完整句式，不要机械把冒号换成逗号：表原因用“因为……”“避免……”或拆成两句，表列举用“包括……”“其中……”“涵盖……”，表条件或对象用“……时”“……下”“……的……”，表目的用“确保……”“以……”。
- 仅保留确有语法或格式作用的冒号：专有名词（如 `Minecraft：Java 版`）、Markdown 标题、段尾引导代码块或列表的冒号（如“示例：”“说明：”“参数：”）、参数或字段定义列表（如 ``- `api_key`：……``），以及界面键值与状态提示模板（如“失败：……”“提示：……”“版本：${version}”）。

## 防御性句子

- 只写实际存在的行为和约束。不要写“适配器不直接调用 Server 内部函数，也不自己写配置文件”“CLI 不依赖 core”“不会创建文件”这类解释“不做什么”的句子；读者用不到这些否定说明。
- 确实需要限制时，写成可执行的条件和结果。例如“命令级权限只能追加更严格的要求，不能降低模块门槛”。
- 不写“不是……而是……”的对照句，也不替读者预设疑问。
- 前因后果按“默认行为 → 失败结果 → 何时例外”排列。例如敏感信息检查：默认执行扫描；不通过时整条消息链被替换；确认内容安全时才跳过。

示例：

> 若页面中存在 Infobox，则会渲染并展示页面中的 Infobox 图片。

> 如果不打算支持此方法，直接在方法定义下设为 pass 即可。

## 段落

- 一段 1–3 句，先给结论，再补原因或边界。
- 长段落指连续正文超过 80 个汉字，且没有分段、列表、小标题或引用块分隔。超过就按语义拆成 2–3 段，不要按句号机械切。
- 代码块前用“示例：”“以下为……”“例如：”引出，说明这段代码做什么。
- 代码块后用“说明：”接列表，逐条解释参数、行为或限制。
- 段落之间靠“若”“当”“因此”承接，不用空泛的过渡语。

## 标题

- 用名词或动宾短语：`介绍`、`包结构`、`最小实例`、`创建实例`、`注册命令`、`命令语法模板`、`正则与定时任务`、`权限`。
- H2 放主题，H3 放子主题，H4 放同一功能的变体或模式。
- 模块页直接用命令名作 H2；教程页用步骤或主题作 H2。
- 不用问句标题，不用空泛的标题。

## 模块使用页

- 开头一句“此模块可以……”，说明用途和适用场景。
- 使用页只写命令行为与结果。配置字段、权重、数据表等技术细节放“安装与开发”页。
- 命令前先列权限（`公开`、`仅管理员`、`仅超级用户`），再写“用法：”和命令。
- 有选项时写“选项：”，每个选项一条。
- 正文按“这条命令做什么 → 参数怎么传 → 结果是什么 → 什么情况下失败”展开。
- 多命令模块按命令拆 H2，不为凑结构强行分组。
- 保留 `CommandUsage`、`ChatExample` 的原有属性和示例内容。

## 教程与开发页

- 先讲目标、前置知识和目录结构，再给最小可运行示例。
- 每节开头用一句话说明“这节讲什么”，然后给代码，再用“说明：”解释。
- 参数、字段、模式用列表逐条写，不塞进长段落。
- 安装、配置、调试按实际执行顺序排列。
- 结尾停在最后一个技术点，不写空泛的收尾。

## 参考页

- 开头用“本文整理了……”，说明覆盖范围。
- 每个对象一个 H2，每个方法一个 H3。
- 方法先给签名代码块，再列参数、返回值、异常；不写教程步骤。
- 目录只列对象名，不重复正文说明。

## 用词

- 解释性正文用日常技术中文。能用具体动作说清，就不用抽象名词。
- 英文缩写、字段名、命令名只在需要精确指代时保留。第一次出现时，用一句中文说明它指什么。
- 同一概念全页用同一个词，不为了显得专业换同义词。
- 不把英文句子逐词翻成中文。先想清楚这句话在说谁做什么，再用中文重新说一遍。
- 句子里的动作要有明确的主语。需要读者操作时，直接写“你”要做什么。
- 不用生硬的名词化动词。写“监控”“交给……处理”“升级操作”“最多等待 10 秒”，不写“监督”“转交”“升级请求”“等 10 秒”。
- 不用缩略名词代替具体对象。写“这个包”“明确授权”“迁移编号”“新增的 key”，不写“同一分发”“显式授权”“号段”“新键”。
- 不写“决定”。按语境写“确定”“取决于”“控制”“从……读取”或“取”。“装载”按安装语境写“加载”。
- 不把“消息链”缩成“链”。写“整条消息链”“新的消息链”。
- 说口令确认时写“原样回复这个口令”，不写“完整回复该口令”；说等待方法取走消息时写“取走”，不写“消费”。

示例：

- 安装前先检查依赖是否齐全。
- 新配置只写进这个实例自己的表。
- 命令执行完后，把结果返回给用户。

## 缩写

- 正文第一次出现英文缩写时，写中文全称加括号原文。例如“拉取请求（PR）”“往返读写（round-trip）”“跨源资源共享（CORS）”。后文直接用缩写。
- 仓库里已经通用的缩写直接使用，不再展开：`CLI`、`TUI`、`API`、`JSON`、`YAML`、`HTTP`、`URL`、`ID`、`RPC`、`AST`、`TLS`、`SMTP`、`SQL`。展开会拖慢阅读，也容易写错全称。
- 代码注释不展开缩写。注释面向维护者，`AST`、`RPC`、`ORM` 在他们的语境里含义清楚。
- 仓库里没有既有用法的缩写必须展开。例如“服务条款（ToS）”第一次出现要写全称，否则读者只能猜。
- 不把英文动词直接拼进中文句子。写“不导入 core”“推送到 gh-pages”“把字符串转成小写”，不写“不 import core”“push 到 gh-pages”“把字符串 lower 掉”。
- 代码标识符、配置键、命令名保持原样。写 `--json`、`AKARI_REPO_ROOT`、`I18NContext`，不翻译成中文。

## 注释

- 注释解释“为什么”，不解释“是什么”。代码已经写明的动作不再复述。
- 单条注释不超过 120 个字符，连续行注释不超过 3 行。写不下就抽函数，或把说明移到文档页。
- 一律用书面语。不写“跑一下”“挂住”“淹掉”“扫掉”“干掉”“一堆”这类口语。
- 注释里不出现“我们”“你”。直接陈述对象、条件和结果，例如“此处检查实例目录是否可写”。
- 不写时间性表述。“暂时”“待补”“目前先”“后续会”都会过期，改成当前的实际约束。
- 非公开的模块、类、函数不加 docstring。公开接口的 docstring 只写用途、参数与返回值。
- 不加装饰性分隔线，也不写“===== 配置 =====”这类分组注释。分组靠文件与函数结构。
- 常量要写清它约束什么。写“单次命令最长等待 5 秒”，不写“超时 5 秒”。

## 版本与数量

- 不把版本号、包数、页面数、模块数写死在正文。它们的值来自包清单、`pyproject.toml`、主题清单或当前仓库，写死后很快会过期。
- 说明前置条件时，写“版本要求见 `docs-theme.json`”或“由主题清单声明”，不要复述具体版本号。
- 描述范围时用“当前仓库中的模块”“每个内置模块”“相关页面”，不要写“有多少个模块”“有多少个页面”这类汇总数字。
- 行为限制是另一回事。例如“最多处理 5 个页面”是代码里的上限，可以保留，但要写清它是行为限制，不是仓库统计。
- 示例输出里的版本号和数量只是示例值，不要当成规格。能改用占位符的就用占位符。
- 依赖约束不要手写版本范围。正文用 `PackageDependencies` 组件，数据由构建时读取包元数据生成。
- 配置模板、接口文档里无法组件化的契约值，按源码原样保留，不要为了去掉数字改动语义。

## 路径与配置

- 包文档目录统一写 `docs/`，不要写旧路径 `doc/`。旧路径只在兼容说明里出现。
- 包文档元数据的默认层是 `docs/config/global/docs.global.toml`，用户覆盖层是 `docs/config/docs.toml`。JSON 版本使用同名 `.json`。
- 实例配置的默认层是 `config/global/<表名>.global.toml` 或 `.json`，用户覆盖层是 `config/<表名>.toml` 或 `.json`。
- `global` 是只读默认层，保存配置只写用户层。用户层没有的键回退到默认层，删除用户键后也回到默认值。
- 写配置说明时先交代默认值来自哪个文件，再写用户层如何覆盖。不要把手写的默认值写成唯一来源。
- 路径、文件名、表名以当前代码和配置为准；不要把旧目录、旧文件名写进操作步骤。

## API 链接

- 核心文档正文里的 API 名称不要手写链接。生成器在构建时按导出清单自动加链接。
- 只链接导出清单里有独立条目的名字。方法名按当前类上下文匹配；跨类时写完整名，例如 `Bot.post_message`。
- 代码块、已有链接不处理。别名、属性或没有独立条目的名字保持纯文本。

## 依赖

- 正文的依赖段用 `<PackageDependencies package="<包 key 或分发名>" />`，不写 `>=`、`<=` 这类范围。
- 组件读取已装包的 `Requires-Dist`，跳过 `extra` 可选依赖。生成器同时按包 key 和分发名建立索引。
- `pyproject.toml` 示例只写包名，并说明实际版本范围从包根的 `dependencies` 读取。
- 组件只在 VitePress 构建产物中渲染。包内 Markdown 仍应能直接读懂。
- 代码块里的依赖示例、`manifest.toml` 的接口字段属于契约，不强行改成组件语法。

### 检查方法

- 改写后逐个搜索上表里的词，命中就按上下文重写整句。
- 不要用批量替换脚本处理这些词。同一个词在不同句子里可能需要不同的说法。
- 替换后复读前后句。句子要能独立读懂，不能只把词换掉。
- 搜索正文里的 `doc/`，确认没有把 `docs/` 写成旧路径；兼容说明例外。
- 搜索正文里的 `>=`、`<=`、`==`，确认依赖段使用组件，代码块和接口字段例外。
- 搜索 `config/global` 与 `docs/config/global`，核对默认层、用户层和回退关系的描述。
- 专项排查非冻结区中的全角冒号“：”，尤其留意代码注释与 docstring 里行尾带冒号、下一行接解释的跨行句型（`：\n# ...`），区分说明式冒号句与应保留的界面模板或定义列表。
- 专项排查电报体单字动词与双字缩写（如“……根”“落盘 / 落库”“已装 / 未装”“判非空 / 判为”“删掉 / 吞掉 / 改挂”），注意排除正常双字词（如“已安装包”“安装完成”“刷新列表”）与代码标识符。
- 专项排查“术语黑话”表中的抽象词（如“门面”“契约”“口径”“判据”“守卫”“基座”“代际”“在途”“替身”“锚定”“短路”“固化”“漂移”），按具体动作或对象改写为日常技术中文。
- 专项排查标点与空格细节：代码元组或行内代码中的全角逗号与冒号（如 `(包名， revision)`、`种类：包名` 改为半角 `,` / `:`）、中文与行内代码或方括号之间缺少空格（如 `基于`loguru`的`、`返回[a, b]范围内`）、中文 docstring 中的半角冒号（`参数:` 改为 `参数：`）、中文句子里的直引号，以及全角标点前的多余空格。

## 格式

- 命令统一用 `~` 前缀；标识符、路径、字段、配置键用行内代码。
- 代码块标语言；命令块保留可直接复制的形式。
- 表格用于参数、字段、权限和平台对照；步骤和注意事项用列表。
- 中文正文用中文引号；代码、命令、URL 原样保留。
- 数字、单位、默认值、版本号照原文，不改写。
- 提交信息使用英文书面语，和 `AGENTS.md` 的约定一致。
- 源码里的用户可见文案与文档同口径。用词调整涉及用户可见文案时，locale、界面文案、示例输出一起改；`mute`、`muted` 这类代码标识符保持原样。

## 截图

- 终端或界面截图要保留页面名称、表头或操作上下文。不要只截一行数据，也不要留大片空白。
- 截图放在页面同级或 `docs/assets/` 下，文件名说明内容；alt 写清画面里是什么。
- 长条截图裁掉无关区域后，仍要能看出它在哪个页面、对应哪张表。
- 图片不能代替文字步骤。图片前后的正文要说明它展示什么。
- 截图保持原格式；品牌资产原图不要为压体积重新编码。

## 冻结区

下面这些位置不参与文风改写。改它们会让示例失真、构建失败或测试报错。

- 代码块与行内代码。示例命令、输出、配置片段要能原样执行。
- 字符串字面量。locale 值、日志模板、错误消息、内嵌脚本里的文本都属于代码，改写会让断言与示例对不上。
- 表格的表头与行列结构。只改单元格里的说明文字，不增删行列。
- front matter、H1、标题层级、站内链接、图片地址、图注。
- `<CommandUsage>`、`<ChatExample>`、`<NoticeBox>` 等组件的标签、属性与示例对话。它们由生成器渲染，或逐字转录实机输出。
- 上游副本与数据文件：`packages/akari-bot-html2text/`、测试录制的 HTTP 响应、曲目数据、许可证头。
- `docs/style-cards/` 自身的词表与示例。

界面文案另有一套口径：`locales/` 下 `zh_cn.json` 的字符串只改术语与标点，感叹号、省略号、表情符号按原样保留。聊天语气是产品的一部分，不改成公文腔。

## 全仓整理

- 按文件量与语言切块，每块不超过 3 万汉字，一个人只读一块。
- 逐句读，只改真有问题的地方。不设“每页必须改几处”的目标，通读后没有问题的文件原样保留。
- 禁止批量替换。同一个词在不同句子里可能需要不同说法，脚本换词必然改坏句子。
- 每改完一个文件就记录进度。同一批的执行可能被中断，进度文件是恢复工作的唯一依据。
- 改完核对结构：`.py` 去掉字符串与 docstring 后语法树必须完全一致，`.json` 与 `.yml` 必须能解析。
- 改完跑五道检查与全量测试，用例结果必须与改动前一致。
- 改用户可见文案时，同时改引用它的文档与断言。同一句话在代码、locale、文档示例、测试断言里各有一份，漏一处就会让示例失真或让用例失败。
- 改动前先统计一次偏差项，改完再统计一次。统计只覆盖叙述文字，代码块与字符串字面量不计入。

### 术语边界

同一个词在不同场合的写法不同。下表是已经定下的边界，按场合取用。

| 场合 | 写法 |
| --- | --- |
| 队列取任务 | 认领，代码注释与文档统一用这个词 |
| 从仓库取得源码 | 克隆仓库 |
| 界面上添加实例 | 添加，散文里写“写入本机实例列表” |
| 写入列表、版本、密钥 | 记录 |
| 代码里的标识符、配置键、命令 | 保持原样，例如 `claim`、`mute`、`--json` |
| 代码里指代真实接口的词 | 保留原词，例如 Fixture、断言库的匹配器、entry points |

### 基于 units.json 的分批复核流程

通过 `.review/units.json` 开展全仓复核并在完成后由外部回填时，按以下流程执行：

1. 先备份原始 `units.json`。复核期间只修改 JSON 内的 `text` 字段，不直接改动源码或文档，也不触碰冻结区路径（`docs/style-cards/`、`packages/akari-bot-html2text/`）及 `<ChatExample>` 块。
2. 不整份读入大文件。用工具按条目类型或筛选条件导出小批量审读视图，逐句阅读，遇到语境不明时只读对应源码或文档核对。
3. 分轮聚焦，先文风后专项。第一轮集中修语序不通、口语词、英文直译和缩写滥用，第二轮专项清理“xxxx：yyyy”说明式冒号句（包含跨行 `：\n#` 注释），第三轮专项排查单字动词与双字缩写，第四轮专项清理术语黑话与剩余缩略语。
4. 将每批改写保存为按 `id` 索引的补丁文件（`[{"id": ..., "text": ...}]`），先跑格式校验再原子写回 `units.json`，保持原有 `ensure_ascii=False`、`indent=0` 与末尾换行格式。
5. 写回后执行全量结构校验，确认 0 错误且工作区仅 `.review/units.json` 有改动：
   - 条目总数、`id` 顺序以及所有非 `text` 元数据与备份完全一致。
   - `py-comment`、`cfg-comment` 的每个非空行均保持原有缩进并以 `#` 开头。
   - `py-inline-comment` 与单行 `py-docstring` 保持单行，且不含未转义三引号。
   - `md-heading` 保持单行与原有 `#` 级别，`md-table` 保持原有行数与每行竖线 `|` 列数。
   - `json-value` 完整保留 `${...}`、`{TERM:...}`、`%s` 等占位符。
   - 冻结区条目 0 修改。

### 基于分册 Markdown 的逐句复核流程

当需要脱离规则筛选、对全仓文本做逐句通读兜底时，可将 `units.json` 拆分为多册 Markdown（例如 `.review/text-01.md` 至 `text-20.md`）按以下流程执行：

1. 严格保持分册标记结构：每个单元由 `<<< UNIT Uxxxxxx ... >>>` 与 `<<< END Uxxxxxx >>>` 包裹，复核期间只改动两行边界之间的正文，绝不修改或增删边界行。
2. 按行流式解析与切片审读：对大体积分册采用逐行读取（避免跨行正则回溯卡顿），按每批约 100–150 条切片顺序通读，确保不因输出截断漏读条目。
3. 补丁按册独立保存与校验：每册改写记录为 `{UID: 新正文}` 补丁文件，写入前去除正文末尾多余换行（防止单行 `py-docstring`、`py-inline-comment` 触发换行校验失败），应用后立即对该册执行格式与冻结区校验。
4. 全册完成后执行 `backfill.py --plan` 只读预演，核对总单元数、改动数与涉及文件数无异常，再确认是否回填仓库源码。

## 逐句复读

改写完成后逐句检查，不能只替换词：

- 主语是否明确，动作与对象是否齐全。
- 前后句是否承接，代词指代是否清楚。
- 能否换成更常见的动词或更短的说法。
- 是否还有连续三层以上从句，或一句话里塞了多个条件。
- 读起来不顺就重写整句，不要只改标点。

## 禁止

- 问句标题，或介绍“本文按什么顺序展开”的句子。
- 口号式、推销式、空洞总结式的表达。
- 长分号链、连续三层以上从句、没有具体内容的背景铺垫。
- 连续正文超过 80 个汉字仍不分段。
- 用旧称代替“禁止发言”，或让文档与源码文案不一致。
- 手写依赖版本范围，或把配置默认值只写在正文里而不指向 `global` 文件。
- 把 `docs/` 写成旧路径 `doc/`，除非在说明兼容读取。
- 比喻、拟人、感叹号、表情符号。
- 为了“更完整”而新增未核实的行为、参数或默认值。
- 只截一行数据、缺少表头或大片空白的界面截图。
- 改写组件属性、表格数据、代码块、图注和示例对话。
- 在叙述句、代码注释或 docstring 中用“xxxx：yyyy”把冒号当万能连接词。
